# Preparing for Evaluation

Building the system is one part of preparing for a DRDO or Smart India Hackathon technical evaluation. Being ready to defend it under direct, skeptical questioning is another, and the team treated the two as separate work. This chapter covers what that preparation looked like: a bank of adversarial questions worked out in advance, a demonstration methodology built as a live engineering walkthrough rather than a feature tour, and the testing discipline that gives both of those things something real to point to.

## The judge question bank

The team compiled a set of adversarial technical questions covering every subsystem, in the voice a senior DRDO propulsion scientist or avionics specialist would plausibly use: questions probing whether the digital twin is a genuine bi-directional twin or a one-way telemetry shadow, whether the physics model is solving real thermodynamics or fitting curves, why particular reference engines and datasets were chosen over classified or proprietary alternatives, whether the AI training data is circular because it was generated by the project's own physics code, why particular model architectures were chosen over larger deep-learning alternatives, how the system tells a genuine mechanical fault apart from a failed sensor, and what happens to system security if a ground link is compromised.

The format the team settled on for each question is itself worth noting as a discipline choice: state what can be answered today with a concrete engineering rationale, cite the exact evidence for that answer, state plainly what cannot currently be answered, and describe the engineering roadmap that would close that gap. Structuring the preparation this way rules out the easy failure mode in a defense setting, where a presenter either overclaims to avoid admitting a limitation or gets caught flat-footed by a question with no prepared answer. Every entry in the bank commits, in writing, to naming its own boundary before a judge finds it.

## Demonstration as a live experiment

The demonstration methodology the team built follows a deliberate philosophy: present the system as a controlled engineering experiment rather than a guided tour of screens. The stated failure mode this avoids is the generic hackathon walkthrough, "here is our dashboard, here are some buttons," which a technical panel has seen many times before and is not persuaded by. The alternative the team built instead sets explicit boundary conditions, establishes a nominal baseline, injects a realistic fault, and traces that fault's effect step by step through the actual detection and diagnosis pipeline, so the judges see cause and effect in the system's own mathematics rather than a narrated slide.

That methodology extends to proving a negative as well as a positive: part of the demonstration is showing that a rapid, legitimate throttle change does not trigger a false alarm, because the physics model predicts the resulting temperature rise and the residual against that prediction stays near zero. Showing that the system stays quiet when it should is as much a part of the evaluation story as showing that it reacts when it should. The demonstration then carries the same fault through anomaly detection, diagnosis, and a prognostic estimate, and into the mission-level consequence of the degraded engine, closing the same loop from propulsion health to mission reliability that motivated the mission planning work described in the previous chapter.

## Testing discipline

Behind both the question bank and the demonstration is a body of automated verification that gives them something to stand on. The backend test suite includes a dedicated family of characterization tests, tests written specifically to pin a headline result as a fixed expectation, so that a later change to the underlying method is caught immediately as a regression rather than surfacing later as a quietly wrong number in a demo. These cover the reliability and FMECA models, the crank-angle telemetry chain, the twin state estimation, the evaluation and validation baseline logic, and the mission executive itself: for example, a characterization test on the crank diagnostics confirms that a healthy simulated engine reports a nominal verdict with firing order 1-4-2-3 and uniform per-cylinder torque contribution, and that an induced misfire is correctly attributed to the affected cylinder. Pinning results like this in an automated test means the numbers quoted to a judge are the same numbers the test suite checks on every run, not a figure that was true once and has since drifted.

Alongside the backend tests, the team ran automated browser-based verification of the ground control station's major workflows, capturing dated screenshot sequences as it went: the multi-engine runtime console and 3D twin for each of the five engine platforms, the voice copilot and its fallback behavior, the mission replay scrubber, and a full mission simulation sequence covering mission planning, live 3D flight, live fault injection, the operator's derate response, mission debrief, and the transition into historical replay. This is UI evidence gathered during development, not a claim of formal certification, but it means the workflows a judge might ask to see live have already been run end to end and recorded once before the room.

## What the process taught

Taken together, the question bank, the demonstration design, and the testing discipline point at the same underlying habit already visible in the previous chapter: treat every claim as something that will be checked, and do the checking yourself first. A system that can answer "what have you not yet validated" as readily as it answers "what does this system do" is in a stronger position under evaluation than one that has only rehearsed the second question. That is the standard the team held itself to in preparing to present ANUMAAN, and it is the same standard this documentation site tries to carry forward.
