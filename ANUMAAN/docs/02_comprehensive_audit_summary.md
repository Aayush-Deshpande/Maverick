# Project ANUMAAN — Comprehensive Audit Summary

**Plain-language status report: what PS-26054 asks for, what we actually have working, what's half-built, and what's still missing.**

> This document exists to answer one question in one place: *"If I had to explain ANUMAAN to someone with zero context, what would I honestly say we've built?"* It is a distillation of two source documents that go into much more depth — read those if you need evidence or citations:
> - The requirement-by-requirement grading: [gap_plan.md](gap_plan.md)
> - The plain-language meaning of the problem statement: [01_problem_statement_breakdown.md](01_problem_statement_breakdown.md)
>
> **Audit basis:** code reading and automated tests across `backend/`, `frontend/`, `apps/`, `data/`, `tests/`, last run 2026-09-17 (73/73 non-LLM tests passing). Passing tests prove the code does what it was written to do — they do **not** prove the twin actually solves the problem statement. That gap is exactly what this document is about.

---

## 1. What Is the Problem Statement, in One Paragraph

DRDO problem statement **PS-26054** asks for a **Digital Twin** — a continuously self-updating virtual copy — of the single piston engine that powers a MALE (Medium Altitude Long Endurance) surveillance drone. These drones fly 18+ hours unmanned with no backup engine, and today's engines are watched by simple threshold alarms ("if temperature > X, alert") that only fire *after* something has already gone wrong. DRDO wants a system that instead combines live sensor data, real engine physics, and AI trained on failure patterns to: catch problems while they're still small, explain what's wrong, say how much life is left in a part (Remaining Useful Life), let engineers simulate a mission before flying it, and let them replay a past flight afterward — all shown on an operator dashboard. Full text: [00_official_problem_statement.md](00_official_problem_statement.md).

**The one-line test for everything below:** a 3D model that looks impressive but doesn't detect or predict anything is not a digital twin — it's a picture. The intelligence has to be real, computed data, not decoration.

---

## 2. The Honest Headline

We have a working, well-tested prototype that implements **every module the problem statement asks for** — physics engine, 20 Hz telemetry, ML anomaly detection, fault classification, RUL estimation, mission replay, a 3D dashboard, maintenance work orders. In that sense, the shape of the solution is complete.

**But one structural issue undercuts the credibility of nearly everything else:** the "simulated engine" and the "digital twin that watches it" are currently *the same model*. The fake sensor readings are generated by taking the twin's own predicted values and adding noise — so when the twin compares "what I expected" against "what I measured," it's always comparing itself to itself plus a fault we told it we were injecting. This means detection cannot actually fail in our current demo, which is the opposite of a convincing proof. Every other capability (prediction accuracy, RUL, anomaly detection) inherits this same weakness, because they all sit downstream of it. This is gap **G01** in the full audit and is the single highest-priority fix.

Everything below should be read with that caveat already applied: a capability marked "working" below works *correctly on the data it receives* — it just hasn't yet been proven against an engine it doesn't already know the answer for.

## 4. What's Partially There, and Why

This is the biggest bucket (39 of 83 requirements). Most of it traces back to a handful of root causes, not 39 unrelated problems:

- **The self-referential simulation (G01)** — described above. Downgrades detection, prediction, RUL, and anomaly detection from "proven" to "plausible but unproven," even though the algorithms themselves are real.
- **Operator controls don't reach the physics (G02)** — changing throttle, altitude, or outside air temperature on the dashboard only changes the *displayed number*, not the underlying simulated physics. Only one control ("regime") actually feeds back into engine behavior. So "simulate a hot-weather mission" doesn't yet produce a physically different engine response.
- **No lead-time or false-alarm evidence (G03)** — the classifier reports 97.5% accuracy, but that's measured on data generated by the same code used to train it, and it only measures per-frame classification, not the thing that actually matters: *how many minutes early did we warn, compared to an old-fashioned threshold alarm, and how many false alarms did we raise over a long normal flight?* Nobody has run that comparison yet.
- **Vibration is a single number (G04)** — the PS asks for "vibration signatures," implying a frequency-spectrum pattern (like a stethoscope). We currently track one RMS (average intensity) value at a sample rate too slow to actually see the frequency content that would distinguish, say, a bearing wearing out from a misfire.
- **Sensor drift detection is switched off (G05)** — the code path exists but the flag that would report "this sensor itself seems to be drifting, not the engine" is hardcoded to never fire.
- **Only one flight phase (G12)** — every simulated mission is "cruise/loiter." The PS explicitly names takeoff, climb, descent, landing, high-altitude, endurance, hot-weather, and rapid-throttle scenarios; only endurance exists today (via a separate script), and only in a form disconnected from the live demo.
- **One dashboard for three audiences (G10)** — the PS wants views useful to operators, propulsion engineers, and maintenance crews. Today there's one operator-style view; the maintenance work-order APIs exist but have no dedicated UI, and there's no engineer-level view showing residuals/spectra/model explanations.
- **Dataset honesty (G18)** — the "real Garmin avionics logs" folder is empty; the closest thing to real degradation data is NASA turbofan data (a jet engine, not a piston engine) relabeled onto our schema. Everything meaningful is synthetic, which is fine *if disclosed*, but any claim of "real data" currently overstates it.

## 5. What's Missing or Not Genuinely There

| Gap | Plain description |
|---|---|
| **Injection timing tracking** | The PS explicitly lists this as one of 8 health parameters to monitor. It does not exist anywhere in the system — no field, no model, no dashboard tile. |
| **Engine performance maps** | The PS asks for reference charts of "what a healthy engine's numbers should look like" at a given RPM/altitude/throttle. We currently compute "expected" values from formulas, not from real manufacturer performance charts. |
| **Adaptive / online learning** | The PS's AI layer is supposed to keep learning. Ours is trained once, offline, and never updates itself from new flights or confirmed maintenance outcomes. |
| **Engine efficiency trends** | Explicitly requested in the dashboard section (fuel efficiency, power margin over time). Not present anywhere. |
| **Real transport / external data ingestion** | Nothing outside our own generator can currently feed the twin — no CAN bus frame encoding, no way to replay an external log "as live." Everything runs in one process talking to itself. |

## 7. What We'd Tell a Judge (or a Friend) Right Now

**The honest pitch:** *"We built every module the problem statement asks for — physics model, 20 Hz telemetry, ML anomaly detection and fault classification, RUL estimation with confidence bounds, mission replay, and a 3D dashboard — and it all runs live, end-to-end, with 73 passing tests. What we haven't yet proven is that the detector would catch a fault it wasn't told about in advance, because right now the simulated 'real' engine and the twin that watches it share too much of the same code. That's gap #1 on our list, and closing it is what turns this from 'a working prototype' into 'a validated prediction system' — which is the actual bar PS-26054 sets."*

**What NOT to claim yet, because it isn't true:**
- "Our model predicts failures before conventional thresholds would" — not measured yet (G03).
- "The dashboard shows the engine's real vibration signature" — it's one averaged number, not a spectrum (G04).
- "Trained on real engine failure data" — effectively all data is synthetic or borrowed from an unrelated engine type (G18).
- "Works for a fleet of different engines" — currently hardcoded to one engine type and one instance (G19).

**What's safe and true to claim:**
- Every PS-named module exists and runs together as one live system, not disconnected demos.
- The ML pipeline (anomaly detection, fault classification, RUL, trend analysis) is real, tested, and mission-isolated so it isn't just memorizing its own training data.
- Mission replay, maintenance work orders, and fleet/region reporting are fully functional.
- The 3D visualization is correctly built as a pure consumer of computed data — deleting it would not remove any actual intelligence.

## 8. What's Needed Next, in Order

The full plan (with acceptance criteria per item) is [gap_plan.md §5](gap_plan.md#5-execution-order). Summarized:

1. **Make the simulation honest** — separate the "fake real engine" from the twin that watches it, so they don't secretly share a brain; make operator controls (throttle/altitude/temperature) actually change the physics.
2. **Prove it predicts** — build an evaluation report that measures warning lead-time vs. a plain threshold alarm, false-alarm rate over long normal flights, and RUL accuracy — the actual evidence a judge would want to see.
3. **Close the explicitly-named gaps** — injection timing, performance maps, real vibration spectra, sensor-drift detection, efficiency trends, role-specific dashboard views.
4. **Add depth** — adaptive learning, finer-grained fault taxonomy, a proper state estimator, history-aware RUL.
5. **Scale and document** — support more than one engine at once, and rewrite the architecture/deployment docs to match what the code actually does (not what was originally planned).
