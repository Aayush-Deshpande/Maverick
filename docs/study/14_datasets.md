# Part XIV — Datasets

*What exists, what it can honestly be used for, and what does not exist at all.*

---

## 14.1 The honest starting position

**There is no public run-to-failure dataset for an aero piston engine on a MALE UAV with the eight PS fault modes labelled.**

I searched for one and did not find it. 🔶 This is unsurprising: such data would require deliberately destroying aero engines while instrumented, and for a defence platform it would almost certainly be restricted.

This fact shapes our entire data strategy, so state it plainly rather than working around it quietly:

| Tier | Meaning | What we can claim |
|---|---|---|
| **Directly relevant** | Same machine class, same faults | None exist publicly |
| **Proxy** | Different machine, transferable *methods* | Method validation only — never "our engine achieves X" |
| **Synthetic** | Generated by our own physics model | Pipeline validation and demonstration — never independent accuracy |

> **The rule:** never present a proxy result as an engine result, and never present a synthetic result as validation. ✅ [Part VIII §8.4](08_fault_diagnosis.md) explains in detail why benchmark numbers do not transfer.

The full catalogue with acquisition instructions lives in [`Datasets/`](../../Datasets/README.md) at the repository root.

## 14.2 Tier 1 — Engine degradation and RUL

### NASA C-MAPSS — Turbofan Engine Degradation Simulation

| Field | Value |
|---|---|
| **Source** | ✅ NASA Ames Prognostics Center of Excellence (PCoE) |
| **URL** | https://www.nasa.gov/intelligent-systems-division/discovery-and-systems-health/pcoe/pcoe-data-set-repository/ |
| **Mirror** | https://phm-datasets.s3.amazonaws.com/NASA/6.+Turbofan+Engine+Degradation+Simulation+Data+Set.zip |
| **Type** | Simulated run-to-failure, multivariate time series |
| **Structure** | ✅ 26 columns: engine ID, cycle number, **3 operational settings** (altitude, Mach, throttle resolver angle), **21 sensors** |
| **Subsets** | ✅ FD001 (1 condition, 1 fault), FD002 (6 conditions, 1 fault), FD003 (1 condition, 2 faults), FD004 (6 conditions, 2 faults) |
| **Labels** | ✅ Training runs to failure; test truncated before failure with true RUL supplied |
| **RUL** | ✅ Yes — this is the standard RUL benchmark |
| **Licence** | US Government work (PCoE repository) — verify current terms at the NASA page |
| **Relevance** | ★★★★ for *method*, ★ for *machine* |

**What it is genuinely good for:**
- Developing and validating the entire RUL pipeline before we have our own data
- Benchmarking against a large published literature — ✅ LSTM, CNN-LSTM+attention, Transformers and GNNs all report on it
- Learning the asymmetric scoring convention ([Part XIX](19_evaluation.md))
- Demonstrating that we handle multiple operating conditions (FD002/FD004)

**What it is not:**
- ❌ **It is a turbofan, not a piston engine.** Completely different thermodynamics, no reciprocating dynamics, no per-cylinder structure, no vibration channel
- ❌ It is simulated, so it lacks real sensor noise, dropouts and installation effects
- ❌ Its sensors are turbofan-specific (fan speeds, compressor pressures) and do not map onto CHT/EGT/oil

⬜ **How we use it:** build and validate the RUL pipeline on C-MAPSS; report our C-MAPSS numbers as *method* evidence; then run the same pipeline on our synthetic piston data and report those separately, clearly labelled.

### N-CMAPSS

✅ A higher-fidelity successor recording run-to-failure trajectories with more realistic flight profiles. Same repository. ⬜ Worth using if C-MAPSS proves too easy.

## 14.3 Tier 2 — Vibration and bearing faults

These are **proxies**. They teach the signal-processing and classification methods from [Part VI](06_vibration_analysis.md) and [Part VIII](08_fault_diagnosis.md). They are not engines.

### CWRU Bearing Data Center

| Field | Value |
|---|---|
| **Source** | Case Western Reserve University |
| **URL** | https://engineering.case.edu/bearingdatacenter |
| **Sampling** | ✅ 12 kHz (and 48 kHz for some drive-end records) |
| **Faults** | Seeded inner race, outer race, ball defects at several diameters |
| **Labels** | ✅ Fault type, size, load condition |
| **RUL** | ❌ No — single-condition snapshots, not degradation trajectories |
| **Relevance** | ★★★ method, ★ machine |

⚠️ ✅ **Documented limitation:** results on CWRU are near-perfect *because of* its controlled laboratory environment. Treat any CWRU accuracy above ~97% as a statement about the dataset, not about the method's field performance.

### Paderborn (KAt-DataCenter) Bearing Dataset

| Field | Value |
|---|---|
| **Source** | Paderborn University, KAt-DataCenter |
| **URL** | https://mb.uni-paderborn.de/kat/forschung/kat-datacenter/bearing-datacenter |
| **Contents** | Both artificially induced **and naturally worn** bearings, with motor current alongside vibration |
| **Labels** | ✅ Fault type and severity |
| **Relevance** | ★★★★ method — **better than CWRU** because it includes naturally-developed damage |

✅ Described in the literature as the more complex dataset, where 1D-CNN accuracy drops to ~95.6% from ~97.6% on CWRU. That gap between a lab-seeded and a naturally-worn dataset is itself a useful lesson about generalisation.

### XJTU-SY Bearing Run-to-Failure

| Field | Value |
|---|---|
| **Source** | Xi'an Jiaotong University / Changxing Sumyoung Technology |
| **Sampling** | ✅ 25.6 kHz, 1.28 s recorded each minute |
| **RUL** | ✅ **Yes — full run-to-failure** |
| **Relevance** | ★★★★ for RUL *on vibration*, which C-MAPSS lacks |

⬜ **Why this one matters to us specifically:** it is the closest public analogue to "predict remaining life from a vibration signal", which is exactly what our vibration-based prognostic path needs to demonstrate. C-MAPSS gives RUL without vibration; XJTU-SY gives vibration with RUL.

### FEMTO / PRONOSTIA

| Field | Value |
|---|---|
| **Source** | ✅ FEMTO-ST Institute, Besançon, France — PRONOSTIA platform |
| **Sampling** | ✅ 25.6 kHz, 0.1 s every 10 s |
| **RUL** | ✅ Yes — run-to-failure, used in the IEEE PHM 2012 challenge |
| **Relevance** | ★★★★ RUL on vibration |

### IMS / NASA Bearing Dataset

| Field | Value |
|---|---|
| **Source** | ✅ Center for Intelligent Maintenance Systems, University of Cincinnati, via NASA PCoE |
| **URL** | https://catalog.data.gov/dataset/ims-bearings · https://phm-datasets.s3.amazonaws.com/NASA/4.+Bearings.zip |
| **Contents** | ✅ Natural bearing defect history — run to failure |
| **Licence** | ✅ https://www.usa.gov/government-works |
| **Relevance** | ★★★★ — **naturally developed** defects, not seeded |

### MFPT

Machinery Failure Prevention Technology society bearing dataset. ✅ Used in the fault-detection literature. Smaller than the others; useful as an additional cross-check.

## 14.4 Tier 3 — UAV telemetry and faults

### ALFA — A Dataset for UAV Fault and Anomaly Detection

| Field | Value |
|---|---|
| **Source** | ✅ Carnegie Mellon Robotics Institute (Keipour, Mousaei, Scherer) |
| **URL** | https://arxiv.org/abs/1907.06268 · https://theairlab.org/alfa-dataset |
| **Contents** | ✅ 47 autonomous flights: **23 sudden full engine failure scenarios** and 24 scenarios across 7 control-surface fault types |
| **Duration** | ✅ 66 minutes normal flight, 13 minutes post-fault, plus many hours of raw data |
| **Labels** | ✅ Ground-truth time and type of fault for each scenario |
| **Relevance** | ★★★ UAV context, ★ engine PHM |

⚠️ **Read the engine-failure scenarios carefully before getting excited.** They are ✅ *sudden full engine failure* on a small fixed-wing UAV — the engine stops. That is a very different problem from our PS, which is about **gradual degradation detected before failure**. ALFA gives us realistic UAV flight telemetry and fault-onset labelling practice, not piston-engine degradation.

⬜ **Best use:** testing our anomaly detector against real flight dynamics data with genuine sensor noise, and practising fault-onset detection-latency measurement.

### UAV-SEAD

State Estimation Anomaly Dataset for UAVs. 🔶 Found in the search; worth evaluating. Focused on state-estimation anomalies rather than propulsion.

## 14.6 Tier 5 — Synthetic (ours)

⬜ Our own physics-based generator, specified in [Part XVII](17_simulation_design.md).

| Field | Value |
|---|---|
| **Source** | Our thermodynamic model + degradation model + fault injection |
| **Contents** | All 8 PS fault modes, all flight phases, configurable environments |
| **Labels** | Perfect — we know ground truth by construction |
| **RUL** | Yes — we can generate full run-to-failure trajectories |
| **Relevance** | ★★★★★ for the PS's fault set, ★ for realism |

**What synthetic data legitimately provides:**
- End-to-end pipeline validation
- Coverage of all eight PS faults, which no public dataset offers
- Controllable fault onset timing for measuring detection latency and prognostic horizon
- Run-to-failure trajectories for RUL development

**What it cannot provide:**
- ❌ Independent validation. If the same model generates training and test data, the evaluation measures the model's ability to invert our simulator, not to diagnose an engine
- ❌ Realistic sensor noise, dropouts, installation effects, real degradation physics
- ❌ Any claim of field accuracy

> ⚠️ **The leakage trap, stated explicitly:** training and testing on data from the same generator is not validation. Any accuracy reported that way must carry the caveat in the same sentence, not in a footnote.

⬜ **Mitigations that make synthetic results more defensible:**
1. Generate test data with *different* parameters — degradation rates, noise levels, environments — than training data
2. Add realistic corruptions the model never saw: dropouts, drift, quantisation, packet loss
3. Hold out entire simulated "airframes" with different baseline characteristics
4. **Cross-validate the method on a public proxy** (C-MAPSS for RUL, Paderborn for vibration) and report both numbers
5. State the limitation prominently in the presentation

Point 4 is the strongest defence: *"our RUL method achieves X on C-MAPSS, an independent public benchmark, and we apply the same validated method to our piston-engine simulation."*

## 14.8 Our data strategy

⬜ Four phases:

**Phase A — Method development on public proxies.** Build and validate each component where established benchmarks exist: RUL on C-MAPSS, vibration classification on Paderborn, vibration RUL on XJTU-SY, multivariate anomaly on SKAB. Report these numbers honestly as method evidence.

**Phase B — Synthetic piston-engine data.** Build the physics-based generator covering all eight PS faults. Validate that the pipeline works end to end on data of the right *shape*.

**Phase C — Cross-validation.** Apply the Phase-A-validated methods to Phase-B data. Report both sets of numbers, clearly distinguished. Never merge them into one headline figure.

**Phase D — Real data acquisition (roadmap, beyond the prototype).** Identify what real data would be needed, and say so in the deployment roadmap: an instrumented Rotax test-cell campaign with a high-rate vibration channel, seeded-fault runs, and ideally a run-to-failure programme. ✅ The PS asks for a "deployment roadmap" as a deliverable, so this belongs there.

🔶 Being explicit that Phase D is required, and that the prototype stands on Phases A–C, is a stronger position than implying the prototype is already validated on real hardware.
