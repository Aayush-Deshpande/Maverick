## 1. Sensor Sanity Validation — before any health computation runs

**The engineering problem this solves:** any monitoring system that reasons about "what the engine is doing" is only as trustworthy as its sensors. A thermocouple with an open circuit, a stuck ADC channel, or an isolated wiring fault produces exactly the kind of sudden, large signal change that a naive anomaly detector would classify as a catastrophic engine fault. In an operational context that's a serious failure mode in the other direction: grounding an aircraft (or panicking an operator) over a broken $40 sensor, not a $40,000 engine. So sensor plausibility has to be checked and separated from engine plausibility *before* anything downstream is allowed to reason about "the engine."

**Implementation** — [backend/physics/sensor_validator.py](../backend/physics/sensor_validator.py), class `SensorSanityValidator`, stateful, called once per 20 Hz frame:

1. **Rate-of-change check.** Each of the 14 monitored channels has a `(max_physical_rate, flag_threshold)` pair derived from the channel's real thermal/mechanical response time — e.g. CHT is capped at 1.5 °C/s physically possible, with anything above 10 °C in one 50 ms frame flagged `RATE_SPIKE` (a cylinder head has real thermal mass; it cannot jump 10 °C in 50 ms without the sensor itself being the problem). EGT, which tracks combustion gas rather than metal mass, is allowed a much faster 8 °C/s before the same logic applies — the limits are per-channel, not one global rule.
2. **Frozen-ADC check.** A rolling 200-frame (10 s) variance is computed per channel; if it drops below a per-channel noise floor for at least `FREEZE_CHECK_MIN_FRAMES` (100 frames / 5 s), the channel is flagged `FROZEN_ADC` — a real analog sensor always has some ripple (calibrated noise σ, e.g. 0.03 bar for oil pressure), so a channel reporting *zero* variance for 5 seconds straight is reporting the same stale ADC value, not a genuinely stable engine.
   - **Why the floor values matter more than they look:** the noise floor for each channel must sit *below* that channel's true calibrated variance, or a perfectly healthy, quiet sensor gets flagged as frozen. The code comment at [sensor_validator.py:49-52](../backend/physics/sensor_validator.py#L49-L52) documents exactly this bug being fixed — oil pressure's floor was previously set *above* its true noise variance (0.001 vs. true ~0.0009), which meant a nominal oil pressure sensor was, on average, already below the "frozen" threshold. This is the kind of threshold-tuning error that produces a demo that looks broken for reasons that have nothing to do with the actual detection logic — worth knowing about if you're tuning any of the other floors.
3. **Cross-sensor correlation check (CHT_2 specifically).** A real thermal event on one cylinder head should have some correlated movement in oil temperature and that cylinder's EGT, because they share a physical heat path. If CHT_2 spikes past 1.1× its physical rate limit *but* OIL_TEMP and EGT_2 stay essentially flat in the same frame, that's evidence the CHT_2 reading itself is the artifact, not a real thermal excursion — this is a second layer of defense specifically for the channel most likely to trigger the highest-severity fault (Fault 1, cylinder overheat), because a false positive there is the most operationally expensive one to get wrong.

**What comes out:** a `SanityReport` with `failed_channels` and a `suppressed_anomaly` flag. Everything downstream — the physics residual comparison, the autoencoder, the Random Forest classifier — receives this report and is required to *exclude* failed channels from its scoring (see `_classify()` in [detection_pipeline.py:410](../backend/ml/detection_pipeline.py#L410), `failed = set(sanity.failed_channels)`, checked before every fault hypothesis). This is what prevents "the CHT_2 sensor died" from being misreported as "Fault 1: Cylinder #2 Overheat" — a distinction the code enforces structurally, not just by convention.

**Known limitation (see the companion audit summary, gap G05):** this validator only catches *acute* sensor failures — a spike or a flatline. A sensor that's slowly drifting (a growing calibration bias of, say, 0.5 °C/min) passes every one of these checks, because each individual frame still looks physically plausible and still has normal variance. The `drift_detected` field exists in the output schema for exactly this case but is currently always `False` — nothing populates it yet. That's a specific, scoped gap, not a design flaw in what's here.

## 2. Physics Residual Model — the "what should this reading be" baseline

**The engineering problem this solves:** you cannot detect an anomaly by looking at a raw sensor value in isolation, because the "normal" value of CHT, EGT, or manifold pressure genuinely changes with RPM, throttle, altitude, and outside air temperature. A CHT of 110 °C is unremarkable at high cruise power and mildly alarming at idle. Any detector that skips this step and works on raw values will either miss real anomalies (because it can't tell "hot because of altitude" from "hot because of a fault") or drown in false alarms (because it flags every normal envelope change).

**Implementation** — `RotaxThermoModel.compute_expected_state()` in [backend/physics/thermo_model.py](../backend/physics/thermo_model.py), called every frame before anomaly scoring: given the current altitude, OAT, RPM, throttle position (TPS), and true airspeed, it computes what every one of the 14 monitored channels *should* read for a healthy Rotax 912 iS under those exact conditions, using closed-form thermodynamic relationships (e.g. manifold pressure as a function of density altitude and throttle position, rather than a lookup table — see gap G07 in the audit summary for why a performance-map-based version is the stated next step). The actual sensor reading minus this expected value is the **residual** — the quantity every downstream detector actually reasons about, not the raw reading. Fourteen residual channels are produced per frame: `d_CHT_1..4`, `d_EGT_1..4`, `d_OIL_PRESS`, `d_OIL_TEMP`, `d_FUEL_FLOW`, `d_MAP`, `d_VIB_RMS`, `d_BUS_VOLTAGE`.

**Why this matters architecturally, not just numerically:** every other ML/statistical component in the system — the autoencoder (§3), the Random Forest and physics-boundary classifier (§4), the trend analyser and RUL estimator (§7) — operates on this same 14-dimensional residual vector, not on raw sensor values. That's a deliberate single point of definition for "what normal means right now," so the different detectors can't quietly disagree with each other about baseline. It also means the whole detection stack automatically re-baselines itself for a different flight phase or environment without any detector-specific code change — climbing to altitude changes the physics model's *expected* MAP and CHT, which changes what counts as a residual, without anyone having to retune the autoencoder or classifier thresholds for "high altitude mode."

## 3. Unsupervised Anomaly Scoring — a from-scratch residual autoencoder

**The engineering problem this solves:** the 8 named fault types are the faults we know to look for. A pure rule-based or classifier-based system can only ever recognize failure modes someone explicitly programmed. An unsupervised anomaly score exists to catch the complementary case: "this combination of residuals doesn't match anything the engine has done before," even without a name for it yet — the "+0.38 °C every 10 minutes" slow-drift scenario the design doc uses as the motivating example, which is a coherent multi-channel pattern that's too small on any single channel to trip a threshold, but too structured across channels to be noise.

**Implementation** — [backend/ml/anomaly_detector.py](../backend/ml/anomaly_detector.py), class `ResidualAutoencoder`. This is a genuinely hand-rolled neural network, not a scikit-learn wrapper — every matrix multiply, ReLU, and backward pass is written in plain Python/lists, deliberately, so the whole model ships as a ~15 KB JSON weight file with zero ML framework dependency (relevant for an air-gapped/edge deployment target, per the PS's edge-computing "desired innovation area").

- **Architecture:** 14 → 8 → 4 → 8 → 14, i.e. a bottleneck autoencoder with the middle layer compressed to 4 dimensions from an input of 14. The bottleneck forces the network to learn a compressed representation of what "normal" residual combinations look like; it can only reconstruct combinations that resemble what it was trained on. ReLU activations on the hidden layers, linear output.
- **Training:** mini-batch SGD with manually derived backpropagation (the gradient chain through all 4 layers is written out explicitly at [anomaly_detector.py:196-283](../backend/ml/anomaly_detector.py#L196-L283)), He/Kaiming initialization for the ReLU layers, mild L2 weight decay (1e-4), trained only on rows labeled `FAULT_ID=0` (nominal flight) — the model never sees a fault example during training, which is the point: it learns the shape of "normal," not the shape of any particular fault.
- **Per-channel normalization is domain-knowledge-driven, not statistically fit.** `RESIDUAL_NORM` hardcodes a `(min, max)` range for each of the 14 residual channels — e.g. CHT residual normalized against −15 °C to +80 °C — chosen from known nominal operating ranges rather than computed from the training data's own min/max. This means the normalization doesn't silently shift if the training dataset composition changes.
- **Scoring formula:** `score = 1 - exp(-k * error / threshold)`, with `k = 1.5` tuned so `error == threshold` maps to a score of ≈0.78 and `2×threshold` maps to ≈0.95 ([anomaly_detector.py:340-349](../backend/ml/anomaly_detector.py#L340-L349)) — an exponential saturation curve rather than a raw linear ratio, so the score stays interpretable and bounded even for wildly out-of-distribution inputs, instead of blowing up unbounded the way a raw reconstruction-error ratio would.
- **Threshold calibration is holdout-aware.** `threshold_99` (the 99th-percentile reconstruction error, i.e. the "this is now clearly abnormal" cutoff) is *not* just taken from the training set's own error distribution. `calibrate_threshold()` exists specifically to recompute it against a held-out validation mission with a deliberately shifted altitude/OAT/RNG seed, because a threshold fit only against training-nominal error tends to run too tight against that intentional distribution shift — see the docstring reasoning at [anomaly_detector.py:314-323](../backend/ml/anomaly_detector.py#L314-L323). This is a direct response to a known failure mode of autoencoder-based anomaly detection: a threshold that looks great on training data and then floods you with false positives the first time conditions genuinely differ from training.

**How it fits into the composite score:** `composite_score = max(ae_score, residuals.anomaly_score)` in the main pipeline ([detection_pipeline.py:335](../backend/ml/detection_pipeline.py#L335)) — the autoencoder's multi-channel pattern score and a simpler physics Z-score (single-channel amplitude spikes) are combined by taking the max, not an average, so a fault that's obvious on one channel alone doesn't get diluted by twelve quiet channels, and a fault that's subtle per-channel but coherent across channels still gets caught by the autoencoder side even if no single Z-score crosses its own threshold.

## 4. Fault Isolation — physics-boundary reasoning with an RF model layered on top

**The engineering problem this solves:** an anomaly score answers "is something wrong?" — it does not answer "what is wrong, and what should the operator do about it?" Going from a scalar anomaly score to one of 8 named, actionable fault diagnoses requires classification, and the two obvious approaches (hand-written physics rules vs. a trained statistical/ML model) have opposite failure modes: hand-written rules are transparent and don't depend on training data quality but can't generalize past what was explicitly coded; a trained classifier generalizes better but is a black box and depends entirely on whether its training data actually spans the real fault-signature space.

**Implementation strategy: run both, with the ML model preferred and the physics rules as a guaranteed fallback** — `_classify()` in [detection_pipeline.py:399-475](../backend/ml/detection_pipeline.py#L399-L475) and the standalone `RotaxFaultClassifier` in [backend/ml/fault_classifier.py](../backend/ml/fault_classifier.py):

1. **Random Forest first.** If a serialized `rotax_random_forest.joblib` model is present, it's queried first with the 14-dimensional residual vector; if its top class isn't "nominal" and its confidence clears `CONFIDENCE_GATE` (0.55), that result is used directly.
2. **Physics-boundary fallback, always available.** If no RF model is loaded, or its confidence doesn't clear the gate, the system falls through to 8 explicit, physically-reasoned scoring functions — one per fault — each combining 2–3 residual signals through a sigmoid to produce a smooth, bounded confidence rather than a hard boolean. For example, Fault 3 (ignition misfire) isn't triggered by "EGT_2 is low" alone; it requires *both* `d_EGT_2 < -35.0` (an absolute drop, unburnt fuel not adding heat on that cylinder) *and* that drop exceeding the average of the other three EGT residuals by 30 °C+ — i.e. the signature is a *relative* runner-to-runner imbalance, not an absolute reading, which is what actually distinguishes a misfire from "the whole engine just got cooler because of a throttle-back." Each fault definition encodes this kind of multi-signal reasoning, not a single-channel threshold — the exact thing conventional threshold monitoring (the approach this system is meant to improve on) cannot do by construction.
3. **Sensor-failure exclusion is enforced at this stage too.** Every one of the 8 physics-fallback checks is gated by `if "<channel>" not in failed:` — a fault hypothesis is never even evaluated on a channel §1 already flagged as sensor-failed, closing the loop between sensor validation and fault diagnosis structurally rather than by convention.
4. **Majority-vote confirmation before anything is reported.** A single frame crossing a fault threshold is not enough to emit an alert — `MajorityVoteBuffer` ([detection_pipeline.py:98-133](../backend/ml/detection_pipeline.py#L98-L133)) keeps the last 10 frames (500 ms at 20 Hz) of raw per-frame fault-id predictions and only confirms a fault if ≥80% of that window agrees on the same fault id. This exists specifically to suppress single-frame false alarms — a fleeting noise spike that momentarily crosses a threshold does not, by itself, produce an operator-facing alert; the signature has to persist.
5. **Alert holdoff.** Once an event is emitted, a 30-second holdoff (`_ALERT_HOLDOFF_SEC`) suppresses further emissions for the same session, so a persistent fault condition produces one actionable event, not a flood of duplicate alerts every frame it remains true.

**What actually comes out of a confirmed fault** is not just a label — it's routed through `DiagnosticAgent.diagnose()` to produce an `ata_chapter` reference, a `manual_reference`, a `root_cause_explanation`, an `emergency_checklist`, and a `maintenance_order`, in addition to the `recommended_action` and the `target_3d_mesh` used to focus the 3D dashboard's camera on the physically affected component. The intent here is that a fault event is a complete package an operator or maintainer can act on immediately, not a bare classification label they have to go interpret themselves.

## 5. Gearbox Vibration Spectral Analysis

**The engineering problem this solves:** mechanical wear (bearing degradation, gearbox tooth wear) has a *frequency signature* long before it shows up as elevated broadband vibration amplitude — a rising 3rd-harmonic prop-order amplitude, for instance, precedes a rise in overall RMS by a meaningful margin. Reasoning only about an RMS amplitude number, the way a conventional vibration alarm does, is exactly the "wait until it's already bad" pattern this whole system exists to move away from.

**Implementation** — `GearboxSpectralAnalyser` ([backend/ml/spectral_analyser.py](../backend/ml/spectral_analyser.py)), stateful, fed the same way as the sensor validator (one `update()` call per frame, cached via `last_spectral_report` so other callers don't perturb its rolling window — the same one-call-per-frame discipline documented at [detection_pipeline.py:338-341](../backend/ml/detection_pipeline.py#L338-L341)). Its output blends into the composite anomaly score when its own `anomaly_score` clears the current composite (`composite_score = max(composite_score, spectral.anomaly_score * 0.8)`), and its `harmonic_ratio` feeds directly into Fault 5's (gearbox vibration) confidence scoring as the preferred signal over raw RMS whenever the analyser reports `ready`.

**Honest limitation, stated directly because it's a real constraint on this feature, not a hedge:** the vibration channel is sampled at the same 20 Hz as every other telemetry channel. The gearbox's meaningful harmonic content (2nd/3rd shaft order at cruise RPM) sits well above the ~10 Hz Nyquist ceiling that a 20 Hz sample rate allows, so the analyser correctly detects that it cannot resolve that harmonic and falls back to an RMS-based estimate rather than fabricate a spectrum from insufficient samples. This is the right failure behavior for the code that exists — it degrades gracefully instead of silently producing garbage — but it means the "vibration signature" analysis is not yet actually running against real spectral content. Fixing this requires the virtual engine to synthesize vibration at ≥2 kHz and extract features (order amplitudes, band energies) at the edge before downsampling to the 20 Hz state link, which is scoped as gap G04 in the companion audit.

## 6. Unified 20 Hz State Service

**The engineering problem this solves:** a digital twin's various consumers — a live dashboard, a 3D visualization client, mission logging, the knowledge graph — need a single, internally-consistent view of "what the engine is doing right now," not each independently polling raw telemetry and potentially disagreeing about timing or derived values.

**Implementation** — `backend/server/engine_service.py` and `backend/server/main.py`: a single service owns the telemetry stream, runs it through the full detection pipeline described in §1–§5, and publishes the resulting unified state over both REST (poll-based) and WebSocket (push-based) at the full 20 Hz tick rate, using a shared schema (`backend/server/schemas.py`) so every consumer — dashboard, 3D twin, replay — is reading the identical structured state, not independently reconstructing it.

## 7. Degradation Trend Analysis + Probabilistic RUL — the prognostics layer

**The engineering problem this solves:** a live anomaly score answers "is something wrong right now." Remaining Useful Life answers a fundamentally different, harder question — "given how this is changing, how much time is left before it becomes a problem" — which requires (a) fitting a trend to noisy time-series data without knowing in advance whether that trend is linear, exponential, or power-law, and (b) turning a point-estimate trend into a *distribution* of possible outcomes, because a single number like "RUL = 40 minutes" with no stated uncertainty is not something a Go/No-Go decision should be based on.

**Implementation** — [backend/ml/trend_analyser.py](../backend/ml/trend_analyser.py), running as a separate daemon thread (`PrognosticsWorker`) on a 20-second cycle, decoupled from the 20 Hz main detection loop via a thread-safe circular buffer (`ScoreBuffer`, lock-protected, 3600-frame/3-minute capacity) so prognostics computation never adds latency to the real-time path:

- **Three fitted model families, selected by AIC, not by which one happens to fit best on the training window alone.** `_least_squares_linear`, `_fit_exponential` (via log-linearization), and `_fit_power_law` (via log-log linearization) are all fit independently to the same windowed data, and Akaike Information Criterion (`n·ln(SSE/n) + 2k`) picks the model that best trades off fit quality against complexity — this is a real, if lightweight, statistical model-selection step, not a hardcoded assumption that degradation is always linear (many real degradation processes, like Arrhenius-accelerated thermal wear, are not).
- **Three window sizes run in parallel per channel** (2 min / 10 min / 30 min — `WINDOW_SIZES_SEC`), because different fault types genuinely evolve at different speeds (oil pressure loss and voltage sag are fast; injector coking and EGT imbalance are slow), and the analyser picks whichever window+model combination produces the best R² for that specific channel at that specific moment, rather than committing to one fixed window for every fault type.
- **A trend is only "real" if `r_squared >= 0.55` and the drift rate exceeds a minimum slope** (`MIN_R2`, `is_trending` gate at [trend_analyser.py:367-368](../backend/ml/trend_analyser.py#L367-L368)) — this exists specifically to prevent the system from projecting a confident RUL number off of what is actually just noise with a marginally positive slope by chance.
- **Time-to-breach is solved by binary search on the fitted curve**, not algebraic inversion (`_time_to_breach`, [trend_analyser.py:402-444](../backend/ml/trend_analyser.py#L402-L444)) — a pragmatic choice that works identically across all three model families (linear, exponential, power-law) without needing a separate closed-form inverse for each, at the cost of a bounded 40-iteration search per query (negligible at a 20-second cycle rate).
- **RUL is a Monte Carlo distribution, not a point estimate.** `ProbabilisticRULEstimator.estimate()` draws 500 perturbed samples of the fitted model's slope and intercept parameters (Gaussian noise scaled by `(1 - R²)/√n`, i.e. lower-confidence fits get proportionally more perturbation), runs the same time-to-breach solve on each perturbed curve, and reports the p10/p50/p90 of the resulting distribution. The Go/No-Go decision downstream deliberately uses the **p10** (conservative/pessimistic bound), not the median — a design choice that means the system is biased toward caution rather than optimism when uncertainty is high, which is the correct bias for a safety-relevant advisory.
- **Go/No-Go logic is a direct three-way comparison**, not a black box: planned sortie duration vs. the worst component's RUL p10, with an explicit safety margin (`SAFETY_MARGIN_MIN`, 2 hours) — `GO` if there's margin beyond that buffer, `CAUTION` if inside it, `NO-GO` if the planned duration already exceeds the conservative RUL estimate. The reasoning string returned alongside each verdict names the specific limiting component and its numeric RUL, so an operator (or a judge) can see exactly which subsystem is driving the decision, not just a status flag.
- **State is explicitly reset on fault-clear, not left to decay implicitly.** `PrognosticsWorker.reset()` exists specifically because forgetting to clear the shared `ScoreBuffer` between scenarios means the trend analyser keeps fitting curves across frames spanning two different fault conditions for up to several minutes, producing a Go/No-Go verdict that's stuck describing an already-resolved scenario ([trend_analyser.py:678-683](../backend/ml/trend_analyser.py#L678-L683)) — a subtle stateful-system bug that's been explicitly designed around, not one that's lurking.

**Separately, a simpler deterministic wear-accumulation model exists in parallel** — `RULEstimator` in [backend/ml/rul_estimator.py](../backend/ml/rul_estimator.py) tracks six named components (cylinder head, fuel rail, ignition harness, oil circuit, gearbox clutch, alternator bus) against baseline lifetime hours, decrementing each based on physically-motivated stress multipliers: an Arrhenius-style exponential thermal stress factor above 115 °C for the cylinder head, a squared penalty for low oil pressure, a cubic vibration-amplitude penalty for the gearbox (mirroring the real cubic relationship between vibration amplitude and fatigue accumulation in rotating machinery), plus a direct multiplier if a fault is actively confirmed on that subsystem. This is a complementary, simpler, always-available RUL signal that doesn't depend on having enough windowed history to fit a trend — useful as a sanity check against the statistically-fitted Monte Carlo estimate, and as the basis for its own independent Go/No-Go advisory (`evaluate_mission_feasibility()`).

## 8. Mission Replay Engine

**The engineering problem this solves:** post-flight investigation needs to answer "what did the twin actually see and decide, minute by minute, during this specific past flight" — which requires storing and re-serving a full time-indexed telemetry stream, not just a final summary, and doing it fast enough for interactive scrubbing (seek to an arbitrary timestamp, not just play sequentially from the start).

**Implementation** — [backend/telemetry/replay_engine.py](../backend/telemetry/replay_engine.py): rather than inventing a second data model for stored telemetry, it deliberately reuses the mission bundle format the mission recorder already produces (`report_dump/mission_NNN/`: `mission.json` manifest, `readings/telemetry_log.csv` time series, `timeline/fault_timeline.json` event markers) — an explicit decision documented in the module docstring to avoid the duplicated-data-model problem that would come from a parallel replay-specific storage format. Each mission's CSV is parsed once and cached in memory as a `_FrameIndex` (sorted timestamp list + parsed rows); `get_frame(t)` does an **O(log n) bisect search**, not a linear scan from the start, so seeking to an arbitrary point in a multi-hour mission is fast regardless of where in the timeline you jump to — the actual requirement for a scrubber UI, where the user can drag to any point at any time. Event markers from the fault timeline are exposed alongside the frame data specifically so a UI can jump directly to "the moment a fault was flagged" rather than requiring the user to scrub blindly looking for it.

## 9. Mission Knowledge Graph, Auto-Generated Reports, and Condition-Based Maintenance

**The engineering problem this solves:** individual detection events are only useful in isolation for a few minutes; the value of "operational history" (used for fleet-level reliability trends, recurring-fault detection, and maintenance planning) only exists if sorties, anomalies, and the maintenance actions taken in response are linked together as a queryable structure, not as disconnected log lines.

**Implementation** — `MissionKnowledgeGraph` in [backend/graph/mission_graph.py](../backend/graph/mission_graph.py) models four explicit node types (`SortieNode`, `SubsystemNode`, `AnomalyEventNode`, `MaintenanceActionNode`) and the relationships between them: a sortie belongs to a region, produces zero or more anomaly events, each of which maps to a subsystem (`_map_fault_to_subsystem`) and can generate a maintenance action that a human inspector later signs off (`sign_off_action`). This is what backs `get_work_orders()`, `get_cbm_summary()` (a fleet-wide condition-based-maintenance summary), and `get_region_comparison()` (comparing reliability across operating theaters/regions) — none of which would be answerable from a flat telemetry log alone, because they require the sortie ↔ subsystem ↔ event ↔ action relationships to actually be modeled as a graph.

On top of the graph, `MissionReporter` ([backend/graph/mission_reporter.py](../backend/graph/mission_reporter.py)) generates a structured Markdown debrief per sortie — frontmatter, mission context, an anomaly/fault timeline built directly from the recorded `AnomalyEventNode`s, prescriptive directives issued, and a CBM table — automatically, from the graph state, rather than requiring a human to manually compile a post-flight report from raw logs.

## 10. 3D Visualization as a Pure Data Consumer

**The engineering design principle applied here:** a 3D model of the airframe/engine is capable of looking impressive while containing zero actual intelligence — every fault-detection decision described in §1–§7 above happens entirely upstream, in backend Python, before any 3D data is touched. The 3D client (`apps/blender_twin/`, `apps/desktop_gcs/`) is architected as a strict consumer of the WebSocket/REST state described in §6: it reads `target_3d_mesh` from a confirmed fault event (see the `FAULT_MESH_MAP` in [detection_pipeline.py:162-171](../backend/ml/detection_pipeline.py#L162-L171)) and uses it only to decide which mesh to highlight and which camera angle to focus — it never independently evaluates whether a fault condition exists. This was a deliberate architectural boundary, not an accident of how the code happened to get organized: the explicit test of that boundary is "if you deleted the entire 3D view, would the system still be able to prove it detects and predicts faults" — and because none of the reasoning in §1–§7 has any dependency on the 3D layer, the answer is yes.

## Summary: What Ties These Together

Every capability above shares three structural properties worth naming explicitly, because they're what separates this from a collection of independent demo features:

1. **A single shared vocabulary.** The 14-channel residual vector computed once in §2 is the only thing every downstream detector (§3, §4, §5, §7) reasons about — no detector invents its own baseline or its own definition of "normal."
2. **Sensor trust is established before engine-health reasoning, and enforced structurally.** §1's `failed_channels` set is threaded into every fault hypothesis in §4 as an exclusion, not advisory metadata a downstream component could ignore.
3. **Every stateful component has explicit reset semantics.** The sensor validator, spectral analyser, majority-vote buffer, and prognostics worker all have a documented `reset()` used at sortie boundaries — because a system that silently carries state across mission boundaries produces exactly the kind of "why is it still alerting on an old fault" bug that's hard to notice in a demo and easy to notice in a real deployment.

What none of this proves on its own — the one thing worth holding onto from the companion audit — is that this detection stack has been shown to work against sensor data it did not itself generate. Every algorithm described above is real and independently sound; the open question the next phase of work has to close is whether it performs this well against an engine it doesn't already know the answer for.

## 11. Features Still To Implement — What PS-26054 Asks For That Isn't Here Yet

Everything above describes what exists. This section is the inverse: capabilities the problem statement requires (or strongly implies) that are absent or only nominally present, each with the technical reason it matters and the concrete build. Gap IDs (G##) refer to [gap_plan.md](gap_plan.md), which holds the acceptance criteria per item. Ordered by priority: P1 items undermine the credibility of everything in §1–§10; P2 items are explicitly named in the PS and missing or broken; P3 items add depth.

### P1 — Credibility blockers

**11.1 Independent virtual engine (G01).** Today `can_streamer.py` builds each "actual" reading as the twin's own expected state plus Gaussian noise plus fault offsets, so residuals are noise + the injected fault by construction and detection cannot fail. Build a separate plant process on the higher-fidelity ODE model in `rotax_dataset_generator.py` (thermal capacitance lag, crank inertia, oil-viscosity coupling) with properties the twin does not know: engine-to-engine parameter variation, sensor bias/lag/noise, slow wear. It publishes only sensor frames over a transport; faults are injected into the plant only; the twin never sees `FAULT_ID`. Nominal residuals must then be non-zero and structured (model mismatch), which is what makes every downstream detector's performance meaningful.

**11.2 Operator commands that drive physics (G02).** `SET_THROTTLE/ALTITUDE/OAT` only overwrite displayed fields after the frame is generated. Route them into the plant as inputs with first-order dynamics (RPM response to throttle, thermal lag on CHT/EGT/oil) so a throttle step yields a transient with a measurable time constant, altitude reduces MAP and power, and OAT raises CHT/oil temperature. Each needs an automated direction/time-constant test. This is the prerequisite for any credible environmental or hot-weather simulation.

**11.3 Evaluation harness proving prediction (G03).** The 97.51% accuracy is per-frame classification on data from the training generator. Build `backend/evaluation/` running the twin against the independent plant on unseen severities, onset rates, engine seeds and regions, reporting: warning lead time versus a plain fixed-threshold monitor (the direct evidence for "transition from threshold-based monitoring"), false alarms per nominal flight hour, RUL error against the plant's known time-to-failure with p10–p90 coverage, and sensor-fault versus component-fault discrimination. One command, fixed seeds, generated report.

### P2 — Explicitly named in the PS

**11.4 Real vibration signatures (G04).** Vibration is one RMS channel at 20 Hz, so `spectral_analyser.py` correctly falls back to RMS (the 3× prop order at ~100 Hz exceeds the 10 Hz Nyquist limit). The plant must synthesize a ≥2 kHz waveform (prop orders 1×/2×/3×, crank order, gear mesh, misfire impulses, bearing tones); an edge extractor computes FFT/order spectra and publishes order amplitudes, band energies, kurtosis and crest factor at 20 Hz. Gearbox wear must raise 3× amplitude before broadband RMS; misfire must be separable from wear; the dashboard gets a spectrum/order plot.

**11.5 Sensor drift detection (G05).** `drift_detected` is hardcoded `False`. Add slow-bias detection using redundancy (four CHT, four EGT channels, FADEC Lane A vs B MAP) plus measured-vs-expected bias estimation (CUSUM or a Kalman bias state), and inject bias-ramp, stuck, noise-growth and dropout faults in the plant. A +0.5 °C/min ramp on one CHT must be reported as sensor drift, while a real cooling fault on that cylinder must be reported as a component fault.

**11.6 Injection timing parameters (G06).** Absent end to end. Add `INJ_TIMING_DEG_1..4`, `INJ_PULSE_MS_1..4`, `IGN_TIMING_DEG` to the schema, model their effect on EGT/power/fuel flow, add an injection-timing-drift / injector-response-delay fault distinguishable from injector clog (fault 2), and carry the channels through state, dashboard, replay, classifier features and dataset schema.

**11.7 Engine performance maps (G07).** Expected values come from algebraic formulas. Add tabulated power, fuel-flow and manifold-pressure maps over RPM × throttle with density-altitude correction, sourced and cited from the Rotax 912 iS operator/installation manual charts, bilinear-interpolated in the expected-state calculation, matching published points within a stated tolerance (proposed 5%) with tests for interpolation and out-of-range handling.

**11.8 Engine efficiency trends (G09).** Nothing exists on the dashboard or in analytics. Compute brake-specific fuel consumption (mapped power over fuel flow), fuel flow versus expected at equal power, and altitude power margin; trend them within a sortie and across sorties/fleet; chart them and include them in mission reports. Injector clog and cooling degradation must visibly shift the trend.

**11.9 Mission profiles and named scenarios (G12).** Live mode is a single `CRUISE_LOITER` phase with sinusoidal altitude. Add mission profile files (phase sequence, durations, target altitude, throttle schedule, ISA deviation, seed) and four selectable presets: High Altitude, Endurance (time-accelerated with wear accumulation), Hot Weather, Rapid Throttle Transitions, each runnable live, in replay and headless, with faults injectable at any phase.

**11.10 Three audience views (G10).** One operator-style dashboard exists. Add an Operator view (status, alerts, action, Go/No-Go), a Propulsion Engineer view (residuals, trends, spectra, model explanations with feature contributions, timing, efficiency) and a Maintenance view (per-component RUL, work-order queue with UI sign-off, advisory history, mission-wise reports).

**11.11 Dataset honesty (G18).** `source1_avionics_logs/` is empty and source 2 is NASA turbofan data. Either obtain licensed real piston-engine logs and parse them with `garmin_parser.py`, or label every dataset as simulated with its generation method and drop or caveat the turbofan-derived RUL grounding, so every claim in docs, UI and slides matches the files present.

**11.12 Architecture and deployment documentation (G20).** Regenerate the architecture document from the real code after G01/G11 and add a deployment roadmap covering edge versus GCS split, test-rig mode, fleet server, the hardware path to real CAN/FADEC, telemetry security and known limitations. Every diagram component maps to a real module or is marked roadmap.

### P3 — Depth

**11.13 External ingestion and transport (G11).** Only the in-process generator feeds the twin; no CAN framing exists. Add virtual CAN via python-can with a documented DBC (SocketCAN on Linux/WSL `vcan`, UDP fallback), a log-as-live mode streaming recorded CSV through the same ingestion path, and an ingestion health view (frame rate, drops, stale channels).

**11.14 Adaptive learning (G08).** Models are trained once. Add per-engine baseline adaptation from flights later confirmed nominal, retraining from sorties using work-order sign-offs as labels, versioned models with automatic before/after evaluation through the G03 harness, and a guard that never adapts across open anomalies (so a slow real fault is not absorbed into the baseline). Record model version in every diagnostic event.

**11.15 Fault taxonomy separation (G13, G14, G15, G16).** Split cooling degradation (slow efficiency loss) from acute overheat; separate combustion instability (cycle-to-cycle RPM/EGT variation, vibration impulses) from misfire and EGT imbalance; extend lubrication beyond pressure loss (oil temperature rise at constant load, viscosity drift, consumption); estimate battery state of health from internal resistance under load steps and alternator capacity versus load, detecting degradation before bus voltage leaves limits. Each is verified as mutually distinguishable in the evaluation confusion matrix.

**11.16 State estimation (G17).** The expected state is steady-state algebra. Add thermal and rotational lag states and a Kalman or observer-style estimator fusing model prediction with possibly faulty sensors, yielding unmeasured quantities such as estimated power and supporting G05; the estimate should track the plant's true internal state better than raw sensors during noise and single-sensor faults.

**11.17 Fleet and multi-engine scalability (G19) and operational history (G21).** No `engine_id`, fault IDs validated 0..8, Rotax constants at module level, fleet summary aggregating sorties not engines. Add engine identity to state and records, engine parameters from configuration, and a fleet view of at least two concurrent virtual engines with separate health, RUL and history. Verify (currently unchecked) that RUL uses cumulative engine hours and that maintenance sign-off adjusts component wear state.

**11.18 Hygiene (G22).** Make the absolute paths in `rotax912_dataset_manifest.json` relative, and align the `_tick` docstring (120 Hz) with the real 20 Hz broadcast.
