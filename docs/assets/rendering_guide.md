# ANUMAAN — 3D Asset Build & Rendering Guide

**You are an autonomous build agent.** Your job is to produce twin-ready, photorealistic Blender models of every MALE UAV and engine listed in §5, inside `ANUMAAN/`, at the quality and functional standard set by two existing baseline files. You will build them with reproducible Python scripts, validate them automatically, render acceptance images, compare those renders against real reference imagery, and iterate until they pass.

**Read this entire file before running anything.** Then work strictly in the order given in §5, keeping the state files in §17 current after every step.

## 1. Mission & Definition of Done

For each target in §5, deliver an asset that is **both** of these at once:

1. **Photorealistic**: matched-angle renders are hard to distinguish from reference photographs in silhouette, proportion, surface detail and material response (operationalized in §12 and §15.4).
2. **Twin-functional**: every fault-relevant component is a separately named, addressable object; the asset responds to fault, ghost, mechanism and camera commands with no platform-specific code; mechanisms are driven by properties, not the timeline (§13).

An asset is **DONE** only when all of the following exist and pass:

- [ ] Manifest JSON (§9), every numeric field sourced in `SOURCES.md`
- [ ] Build script that regenerates the `.blend` from a clean state
- [ ] `.blend` output (and LOD1 for engines)
- [ ] `validate_asset.py` report with **zero FAIL** (§14)
- [ ] Full acceptance render set (§15.3)
- [ ] `REVIEW.md` reference comparison with every checklist item passed or explicitly waived by the user (§15.4)
- [ ] `PROGRESS.md` row marked DONE with links to all of the above

### 6.2 IDs

Lowercase snake_case, exactly as in §5. File names, manifest IDs and collection prefixes all derive from the ID.

### 6.3 Object naming contract

| Asset | Pattern | Example |
|---|---|---|
| Engine component | `{Component}_M_{Material}_{n}` | `Turbocharger_LP_M_CastIron_0`, `Injector_3_M_Steel_0` |
| Engine sensor | `Sensor_{Channel}_M_{Material}_{n}` | `Sensor_EGT_3_M_Steel_0` |
| Airframe part | Descriptive PascalCase with side suffix | `Wing_Outer_Right`, `Main_Gear_Strut_Left` |
| Pivots / mounts | `Pivot_{Mechanism}[_{Side}]`, `Engine_Mount_{n}` | `Pivot_Aileron_Left`, `Engine_Mount_1` |
| Cameras / targets | `Cam_{Name}`, `Target_Cam_{Name}` | `Cam_Engine_Bay` |
| **Mounted engine objects** | `E{n}__` prefix + engine object name | `E1__Injector_3_M_Steel_0` |

Rules:

- `{n}` starts at 0 and increments; **never** leave Blender's `.001` suffixes. After every `obj.name = x`, assert `obj.name == x`.
- Components use the canonical names in §9.4. Do not invent synonyms.
- `Left`/`Right` are from the aircraft's point of view: **Right = +X**.

### 6.4 Materials

- Engine materials follow the Rotax library style `M_{Material}` and are shared across objects: reuse `M_Steel, M_SteelDark, M_Chrome, M_Cobalt, M_Copper, M_Rubber, M_PlasticBlack, M_MetalPaintedBlack, M_Labels`; add as needed, e.g. `M_CastAluminium, M_CastIron, M_HeatTintedSteel, M_BraidedHose, M_TurboHousing`.
- Airframe materials are prefixed with a platform code: `TAPAS_Skin_PBR`, `MQ1_Skin_PBR`, following `TB3_Tactical_PBR`.
- Per-object fault and ghost state is **never** done by duplicating materials. Use object attributes (§13.1).

### 6.5 Coordinates & units

- Metres, real-world scale, scene unit scale 1.0.
- Airframe: **nose +Y, up +Z, right wing +X**. Root empty at the origin; lowest landing-gear point at **Z = 0.000 m**.
- Engine: crankshaft/propeller axis along Y, **propeller flange face centre at the origin**, propeller side toward +Y, top of engine toward +Z. The root empty `<ENGINE_ID>_Root` sits at the flange centre.
- Mount rotation for a pusher is 180° about Z. It lives in the platform manifest, not in the engine file.

## 8. Phase 1: References & Specifications

### 8.1 Triage what exists

The existing `REFERENCE_CATALOG.md` / `IMAGE_CATALOG.md` files are machine-generated. Every image is labelled "CONFIRMED / suitable for 3D", and at least one "orthographic" file (`Bayraktar_TB2/01_Orthographic/Bayraktar_TB2_01_Orthographic_013.png`) is actually a world map of operator countries. **Ignore those grades.**

For each platform folder and engine folder, open and look at **every image**, then write `TRIAGE.md` with one row per file:

| File | Grade | Shows | Notes |
|---|---|---|---|

Grades:

- `USABLE-ORTHO`: true top, side or front orthographic or near-orthographic view of the correct aircraft/engine variant
- `USABLE-DETAIL`: clear photo or diagram of a specific region (gear, turret, engine side, markings)
- `CONTEXT-ONLY`: correct subject but too small, distant, or ambiguous to model from
- `REJECT`: wrong subject, wrong variant, map, logo, chart, collage, watermark-dominated, AI-generated, or a render of someone else's 3D model

Also record the variant shown (e.g. TB2 vs TB3, Heron vs Heron TP, Predator vs Gray Eagle). Wrong-variant images are the most common trap.

### 8.2 Acquire missing references

Minimum per airframe before modelling (Gate A):

- [ ] ≥ 1 `USABLE-ORTHO` each for **top, side and front**
- [ ] ≥ 6 `USABLE-DETAIL` covering nose/sensors, wing root, tail, landing gear, engine installation and propeller, markings
- [ ] Wingspan, length and height from **≥ 2 independent sources agreeing within 2%**

Minimum per engine:

- [ ] ≥ 4 `USABLE-DETAIL` views from different sides, including ≥ 1 annotated component diagram or cutaway

## 10. Engine Build Procedure

### 10.1 Common steps (every engine)

1. Manifest complete through Gate A.
2. `build_<engine_id>.py`: `reset_scene`, create the collection tree (§10.2), create `<ENGINE_ID>_Root` at the origin.
3. Geometry by the source-specific method (§10.3–10.6).
4. Assign `M_*` materials with twin nodes (§13.1).
5. Name every object per §6.3; assert that every manifest object exists.
6. Place sensors (§9.4).
7. Add custom property `twin_component` (the component key) to every object, and `twin_sensor_channel` to sensor objects.
8. Cameras: `Cam_Hero`, `Cam_Beauty_Orbit`, `Cam_Wireframe`, plus one TRACK_TO camera per subsystem closeup used in §15.3.
9. Studio lighting (§15.2); also create an `Environment` collection holding a ground plane, excluded from LOD1.
10. Embed the controller (§13.4).
11. `pack_and_save` to `Models/engines/<engine_id>.blend`.
12. **LOD1:** reopen the output in a second pass, apply Decimate (collapse) per object until the total is ≤ 400 k tris, keep **identical object names**, remove cameras/lights/environment, save `<engine_id>_lod1.blend`.
13. Validate (§14), render (§15), compare (§15.4), iterate.

## 12. Realism Standard ("pixel-perfect")

Realism comes from **surface response and imperfection**, not polygon count. The TB3 baseline's gap is exactly this. Required layers:

### 12.1 Airframe skin

| Layer | Implementation | Visible result |
|---|---|---|
| Base paint | Sourced colour; subtle large-scale value noise (±2%) | Not a flat CG colour |
| Panel seams | Normal-map grooves plus a cavity-darkening AO multiply | Panels readable at hero distance |
| Fasteners | Rivet/screw rows along panel edges in the normal map, slight roughness difference | Visible in closeups |
| Edge wear | Pointiness/curvature-driven mask on leading edges, panel corners and access doors: slightly lighter, lower roughness | Handling wear |
| Grime & dust | AO- and gravity-driven mask (more on lower surfaces and near the gear) | Aged service aircraft |
| Exhaust staining | Gradient streak aft of each exhaust outlet, following the airflow direction | Engine installation reads as real |
| Fluid streaks | Faint oil/fuel stains below cowling vents and filler caps | Operational realism |
| Roughness variation | Noise-broken roughness per panel (±0.05) | Reflections break up realistically |
| Composite vs metal | Composite skin non-metallic; metal parts metallic with fine anisotropic scratches where references show | Correct material response |
| Glass / optics | Transmission with a thin-film tint for sensor windows; separate glass and gimbal materials | Turret reads as optical |
| Tyres | Rubber with sidewall text/tread in the normal map, dust on the lower half | — |

### 12.2 Engine

| Layer | Implementation |
|---|---|
| Cast aluminium / iron | Fine grain noise bump, casting parting lines, slightly rough (0.45–0.6) |
| Machined faces | Lower roughness with concentric tool-mark anisotropy on flange faces |
| Heat tint | Blue→straw→brown gradient on exhaust runners near the ports; turbine housing darkened |
| Hoses | Braided or ribbed normal detail, rubber sheen, clamps with screw heads |
| Paint | Painted parts (e.g. gearbox housings shown painted in references) with edge chips |
| Oil film & grime | Faint darkening in crevices around gaskets, drain plugs and the turbo oil return |
| Labels | Manufacturer plates and warning labels baked into UVs at referenced positions |
| Wiring | Loom with sleeves, P-clips every ~150 mm, connectors with coloured locks |

### 12.3 Rules

- All masks are procedural or baked from procedural shaders. No photo textures (H5).
- Materials must render correctly in **both** EEVEE (interactive) and Cycles (acceptance). Check both.
- Bake heavy procedural node trees on the airframe skin to image maps (4K) so EEVEE stays interactive; engines may keep procedural materials if EEVEE viewport ≥ 30 FPS on LOD0.

## 13. Twin Functional Layer

### 13.1 Material twin nodes (every material, engines and airframes)

Per-object state is read from **object custom properties** through `ShaderNodeAttribute` nodes with `attribute_type = 'OBJECT'` (confirm in the probe, §7.2). One shared material can then show a different state on each object.

| Object property | Type / range | Shader effect |
|---|---|---|
| `twin_fault_level` | float 0–1 | Emission strength = level × 8 |
| `twin_fault_rgb` | float[3] | Emission colour |
| `twin_ghost` | float 0–1 | Mix toward the ghost shader (fresnel-weighted cyan emission + transparency, same look as TB3 X-ray) |
| `twin_sensor_suspect` | float 0/1 | Magenta/white striped emission using object-space coordinates, for sensor objects only |

Rules:

- Node names are part of the contract: `TwinFaultLevel`, `TwinFaultRGB`, `TwinGhost`, `TwinSensorSuspect` (the attribute nodes); `XRayFactor` (Value node) on skin materials.
- Ghost amount = `max(XRayFactor, twin_ghost)`.
- Transparency: set `surface_render_method` (or `blend_method`, whichever the probe shows) so ghosting works in EEVEE.
- Defaults are 0 on every object, so nominal renders are unaffected.
- After changing a property from Python: `obj.update_tag()` then `bpy.context.view_layer.update()`.

**Fallback:** if the probe or the C18 test shows object attributes do not update in EEVEE, switch to the standalone app's approach (store original materials, swap in per-object override materials, restore exactly). Record the switch in `BLOCKERS.md`.

Fault colour ramp (severity × confidence):

| State | RGB |
|---|---|
| Degrading, no fault | (1.0, 0.75, 0.1) amber, level ≤ 0.35 |
| MINOR | (1.0, 0.85, 0.0) |
| MAJOR | (1.0, 0.45, 0.0) |
| CRITICAL | (1.0, 0.05, 0.02) |
| Unclassified anomaly | (0.75, 0.35, 1.0) violet |
| Sensor suspect | magenta/white stripes via `twin_sensor_suspect` |

Visual priority when states conflict: sensor suspect → critical → major → minor → unclassified → degrading → nominal.

### 13.2 Scene properties (airframes and engines)

| Property | Meaning |
|---|---|
| `twin_platform_id` / `twin_engine_id` | Identity; must match the manifest |
| `twin_time_s` | Twin clock in seconds (live or replay). **Never derived from the frame number** |
| `prop_rpm_E{n}` | Propeller RPM per engine mount |
| `gear_retract`, `wing_fold`, `aileron`, `elevator`, `rudder`, `flap` | Mechanism inputs, 0–1 or −1..1 |
| `display_mode` | 0 PBR, 1 ghost, 2 internal only, 3 wireframe clay |

### 13.3 Drivers, not keyframes

- Mechanism pivots: driver on the rotation channel, expression `prop * max_angle_rad` using SINGLE_PROP variables targeting the scene property.
- Propeller: driver on the spin axis, expression `t * rpm / 60.0 * 6.283185307`, with `t` = `twin_time_s` and `rpm` = `prop_rpm_E{n}`.
- Blur disc: driver on `hide_render`/`hide_viewport` (or a material alpha), shown when `rpm > 300`; blades hidden at the same threshold.
- Keep driver expressions to plain arithmetic so they evaluate without Python auto-execution.
- **No `animation_data.action` on any mechanism, pivot or propeller object** (C11).
- For renders that need motion, the render script sets `twin_time_s` per frame; the drivers stay the same.

### 13.4 Controller

Write one template, `scripts/lib/anumaan_twin_controller.py`. The build script embeds it as a text block `<asset_id>_ui_controller.py` with `use_module = True`, alongside the manifest JSON as a second text block `<asset_id>_manifest.json`. The controller must contain **no platform-specific names**; everything comes from the embedded manifest.

Panel features:

- Display modes (sets `display_mode` and the `XRayFactor`/`twin_ghost` values)
- Subsystem isolation by collection
- Mechanism sliders for mechanisms listed in the manifest only
- Camera buttons for cameras listed in the manifest only
- **Fault preview:** dropdown of manifest faults + severity slider. It sets `twin_fault_level`/`twin_fault_rgb` on the target component objects (with the `E{n}__` prefix in airframes), sets `twin_ghost = 0.85` on everything else, switches airframes to ghost mode, and moves `Cam_Beauty_Orbit` to the fault's `inspect_pose` (transformed through `Engine_Mount_{n}` in airframes)
- **Sensor preview:** pick a sensor channel → `twin_sensor_suspect = 1` on its sensor objects, with **no** component fault highlight
- **Clear:** restores every twin property to 0 and cameras to default
- Pulsing (optional, interactive only): a timer modulates `twin_fault_level` for display; renders use static values

## 14. Validation: `scripts/validate/validate_asset.py`

Usage (PowerShell): `& "E:\Blender\blender.exe" --background "<asset.blend>" --factory-startup --python "ANUMAAN\scripts\validate\validate_asset.py" -- --manifest "<path>" --report "ANUMAAN\build\reports\<asset_id>_validation"`. Writes `.json` and `.md`; exits non-zero on any FAIL. Checks marked WARN are reported but do not fail.

| ID | Check | Threshold |
|---|---|---|
| C1 | Every object named in the manifest (components, sensors, pivots, cameras, blur discs; with `E{n}__` prefixes in airframes) exists exactly once | 100% |
| C2 | No object, material, collection or image name ends in `.\d{3}` | 0 |
| C3 | Airframe: minimum Z of `Landing_Gear` geometry | 0.000 ± 0.005 m |
| C4 | Airframe bounding box (excluding `Environment`, `Cameras`, `Lighting`, blur discs) vs manifest wingspan/length/height | ±2% (±5% if `dimension_confidence` = LOW) |
| C5 | Required collections exist and are non-empty (§10.2 / §11.1) | All |
| C6 | Every material has the §13.1 twin attribute nodes; every airframe skin material has `XRayFactor` | All |
| C7 | Manifest cameras exist; perspective cameras have TRACK_TO to an existing target | All |
| C8 | No decal planes: no object with ≤ 12 faces whose material or name contains `Decal`, `Marking`, `Roundel`, `Flag` | 0 |
| C9 | Triangles at viewport: airframe ≤ 150 k; engine LOD0 ≤ 2.5 M; LOD1 ≤ 400 k; airframe file incl. mounted engines ≤ 1.0 M | Hard limit |
| C10 | All images packed; airframe skin maps 4096²; no image missing | All |
| C11 | Mechanism, pivot and propeller objects have **no** `animation_data.action` and **do** have drivers | All |
| C12 | Scene METRIC, METERS, scale 1.0 | Exact |
| C13 | Build determinism: run the build twice; identical sorted object-name lists and per-object tri counts | Exact |
| C14 | Every mesh using an image texture has a UV map | All |
| C15 | Normals: fraction of faces flipped relative to recalculated outward normals, per object | ≤ 1% (WARN instead of FAIL for objects with non-manifold edges, where recalculation is unreliable) |
| C16 | Sides: objects named `*_Right`/`*_R` have centroid X > 0, `*_Left`/`*_L` X < 0 | All |
| C17 | Manifest scene properties exist (`twin_*`, mechanisms, `prop_rpm_E{n}`) | All |
| C18 | **Fault render test:** for each manifest fault, render 320×180 EEVEE from the inspect pose twice with ghosting disabled: nominal, then with only `twin_fault_level`/`twin_fault_rgb` set on the target objects. Then clear, and verify every twin property is 0 and material assignments hash identical to before | All faults |
| C19 | **Framing test:** with the camera at each fault's inspect pose, all 8 bounding-box corners of the target component project inside the frame via `bpy_extras.object_utils.world_to_camera_view` (0 ≤ x,y ≤ 1, z > 0) and the projected box covers ≥ 15% of the frame | All faults |
| C20 | **No placeholder components:** each manifest component has ≥ 300 tris total and is not a bare primitive (8-vertex box, default cylinder/sphere vertex counts) | All |
| C21 | Sensor test: setting `twin_sensor_suspect` on a sensor changes only that sensor's pixels (same method as C18) | All sensors |
| C22 | Mount alignment: each propeller hub within 5 mm of the mounted engine's `Prop_Flange` | All mounts |
| C23 | Mechanism test: set each mechanism to 0 and 1; pivots rotate by the manifest angles ±0.5°; setting `twin_time_s` alone does not move any non-propeller pivot | All |

### 15.4 Reference comparison loop (the realism gate)

Write `scripts/tools/compose_compare.py`. It uses Blender's bundled numpy and `bpy.data.images`; do not assume Pillow is available.

For each airframe or engine:

1. Pick **all** `USABLE-ORTHO` references and **≥ 5** `USABLE-DETAIL` references covering different regions.
2. **Orthographic overlay:** render the matching ortho camera with transparent film, scaled so the manifest dimension matches the reference's scale; composite at 50% opacity over the reference; also save side by side. Output `compare/ortho_<view>_overlay.png`.
3. **Matched-angle photo comparison:** for each detail reference, create a camera that reproduces the photo's viewpoint (estimate focal length from visible perspective; iterate position until key feature points line up), render with the rig closest to the photo's lighting, and compose side by side at equal height. Output `compare/detail_<nn>_side_by_side.png`.
4. Look at every composite image and fill `REVIEW.md`:

```markdown
## Comparison <nn>: <reference file> vs <render file>
| Check | Result | Deviation (if any) | Fix applied |
|---|---|---|---|
| Silhouette / outline (ortho: edges within ~1% of span) | PASS/FAIL | | |
| Proportions (nose, wing position, tail, gear stance) | | | |
| Component presence (every visible part in the reference exists) | | | |
| Component placement | | | |
| Markings: position, size, colour | | | |
| Paint colour and sheen | | | |
| Material response (metal vs composite vs rubber vs glass) | | | |
| Surface detail density (panels, fasteners, hoses, wiring) | | | |
| Wear / grime plausibility | | | |
```

5. Fix every FAIL in the **build script**, rebuild, re-validate (§14), re-render, re-compare.
6. Allow up to **5 iterations** per asset. Any FAIL left after 5: record it in `BLOCKERS.md` with the composite image paths and ask the user whether to accept, supply better references, or continue.

An asset passes the realism gate only when every checklist row in every comparison is PASS or explicitly waived by the user.

## 18. Blender 5.2 Pitfalls

| Pitfall | Correct approach |
|---|---|
| Old Principled BSDF socket names (`Specular`, `Emission`, `Subsurface`, `Clearcoat`, `Transmission`) | Use the socket names from `blender_api_probe.json` |
| `mesh.use_auto_smooth` | Removed. Use shade-auto-smooth / "Smooth by Angle" |
| `bpy.ops.import_mesh.stl` / `import_scene.obj` | Use `bpy.ops.wm.stl_import` / `bpy.ops.wm.obj_import` (verified present) |
| `scene.eevee.use_gtao`, `use_ssr` | May not exist; follow the probe and guard with `hasattr` (as the TB3 script does) |
| `material.blend_method` | May be superseded by `surface_render_method`; use the probe |
| Operators needing a 3D viewport context in background mode | Prefer `bmesh` and data-API calls; avoid `bpy.ops.object.mode_set` loops on thousands of objects |
| Blender silently renames `X` to `X.001` on collision | Assert names after every assignment (§6.3) |
| Unpacked image paths `//textures/...` break when files move | `bpy.ops.file.pack_all()` before saving (both baselines pack) |
| Add-on noise and registration side effects | Always `--factory-startup` |
| Changing custom properties does not refresh the shader | `obj.update_tag()` + `view_layer.update()` |
| Large saves | `save_as_mainfile(..., compress=True)` |
| Windows paths | `pathlib.Path`; never build paths by string concatenation |
| Linked library data is read-only | Append mounted engines (§11.6) |
| Look enum names depend on the active view transform | Set `view_transform = 'AgX'` first, then pick the look name listed by the probe |
