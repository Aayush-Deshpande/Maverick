PART 0 - THE "COMPLETELY DYNAMIC" RULE
=====================================================================================================================

0.1 Definition (all ten must hold)
D1. Every number shown anywhere comes from one of exactly four places:
    (a) the physics simulation stepping at runtime;
    (b) a recording being replayed;
    (c) a real or virtual data bus (CAN/MAVLink);
    (d) a configuration value with a source tag (limits, rated power, geometry).
    Nothing is typed into code as a reading. A constant in code is allowed only as a physical constant (gas constant
    287.05 J/kg/K, g = 9.80665) or a numerical setting (step size). It needs a named variable and a comment.
D2. Every reading moves because something upstream moved. If a lever, the environment or a fault changes, every
    dependent output changes in the physically right direction. No output stays frozen while its inputs change.
D3. Faults change component parameters, never outputs (R 21.6). The readings then change because the equations run.
D4. Diagnosis, status, highlights, RUL and maintenance advice are computed only from measured data (the Frame). They
    never read the injected-fault list, the plant truth, or the command history. "Training mode" may display the
    commanded fault next to the result, labelled COMMANDED.
D5. Engines, faults, components, limits, sensors, presets and UI labels are DATA. They live in:
    configs/engines/*.json, configs/faults.json, configs/components/<engine>.json, configs/sensors/<engine>.json,
    configs/missions/*.json, configs/ui/*.json.
    UI menus, 3D profiles, fault lists, gauges and limit lines are built from these at runtime. To add a 6th engine
    you add a config, a GLB and a component manifest, with zero code changes. To add a fault you add one registry
    entry pointing at an existing model parameter, again with zero code changes.
D6. Rates and timing are measured, not printed. The UI shows the actual publish rate and data age from the state
    message. Today it shows static "20 Hz" labels.
D7. There is no silent fallback. If a value is missing the UI shows "NO DATA" with the reason; it never shows a
    default (today: `f.bus_v or 14.1`, `frame.oil_p or 3.5`, offline sine telemetry). If a fault is not applicable
    the API rejects it with the reason; it never ignores it.
D8. There is one source of truth per running engine. Every client (React console, 3D viewer, Blender app, phone)
    reads the same state message stream and sends commands through the same API.
D9. Time is simulation time. Detection, trends, RUL and replay use sim_time_s, so the 1x/5x/20x/60x time scale
    changes nothing but speed.
D10. Everything is deterministic for a given seed and command log, so any sortie can be reproduced exactly, which
    makes replay and "what-if" forks possible.

0.3 How the rule is enforced (tests run in CI; they live in tests/dynamic/)
T-DYN-1 Static scan. A test parses backend/sim, backend/runtime, backend/server and frontend/src.
        - It fails on numeric literals assigned to reading fields (fields listed in the state schema).
        - It fails on `or <number>` fallbacks for readings.
        - It fails on engine IDs or fault names in code outside configs/ and tests/.
        - Allowed literals are in tests/dynamic/allowlist.txt, each with a reason.
T-DYN-2 Frozen-channel test. Run every engine for 120 s of simulated time with throttle sweeping 30->100->30 % and
        altitude 0->15,000 ft. Every channel declared "load-dependent" in configs/sensors/<engine>.json must change
        by more than 5 sensor-noise sigmas. Any channel with zero variance fails.
T-DYN-3 Perturbation test. From a trimmed cruise point, change one input at a time: throttle +10 %, altitude
        +2,000 ft, OAT +10 C, humidity +40 % RH, airspeed +10 kt, prop rpm setpoint +100. Each output must move in
        the sign given by the expected-sensitivity table (configs/sensors/<engine>.json "sensitivity" block).
        Example: OAT up -> NA engine power down, CHT up, oil temperature up.
T-DYN-4 No-truth-leak test. The detection/diagnosis/status/prognostics modules must not import backend.sim.faults,
        the plant truth, or the fault manager (import graph check). Running the same recorded Frames twice, once
        with the active-fault list visible and once with it hidden, must give byte-identical diagnosis, status,
        highlights and RUL.
T-DYN-5 Add-an-engine test. CI copies configs/engines/rotax_912is.json to "test_engine_6cyl" with 6 cylinders,
        different bore/stroke and rated power, plus a placeholder GLB and manifest. Then:
        - the server starts, calibrates, and lists it;
        - the UI shows it in every menu (Playwright);
        - faults filter by applicability;
        - per-cylinder faults offer cylinders 1-6.
        No code file changes.
T-DYN-6 Add-a-fault test. CI adds a registry entry "TEST_COOLING_X" that changes an existing parameter (cooling
        effectiveness, cylinder 1). It must appear in every fault menu, change CHT_1, be detected and isolated by
        its signature, and highlight the parts listed in its component entry. No code file changes.
T-DYN-7 Determinism. Same seed + same command log -> identical Frames (hash compare) on two runs and after a replay.
T-DYN-8 No-silent-fallback. Kill a sensor channel (S05 dropout): the UI shows NO DATA / VIRTUAL with the reason; the
        state message never contains a default value for that channel.

      - ν = δ/2, where δ is the smallest shift to detect in sigma units (start δ = 1).

---------------------------------------------------------------------------------------------------------------------
M4 - PROGNOSTICS, TRENDS, MAINTENANCE, ADAPTIVE LEARNING (weeks 5-6)
---------------------------------------------------------------------------------------------------------------------
Step 4.1 Degradation processes in the plant (backend/sim/wear.py). Slow wear laws drive registry faults over
  operating hours:
  - bearing wear rate ∝ load x lubrication factor (low oil pressure/high temperature accelerate it);
  - cooling-fin/radiator fouling ∝ dust exposure;
  - injector coking ∝ hours at low load (CI);
  - turbo bearing wear ∝ shaft speed and oil temperature;
  - battery capacity fade per cycle.
  With these, run-to-failure trajectories can be generated with known truth.
Step 4.2 Trends: robust slope (Theil-Sen) on health parameters and on limit-relevant readings over sliding windows
  (10 min, 1 h, mission). Time-to-limit = (limit - current)/slope, with a confidence interval from the slope
  interval. It is shown only when the slope is significant.
Step 4.3 RUL:
  - train a model (gradient boosting first; a small LSTM optional) from health parameters + operating history to RUL
    on simulated run-to-failure fleets (≥200 trajectories per engine, different seeds/missions/environments);
  - split conformal intervals with a calibration set of 10-20 % of trajectories held out BY TRAJECTORY (not by
    sample);
  - target 90 % coverage and report empirical coverage. Published work on turbofan and bearing RUL reports 88-92 %
    against a 90 % target with this method.
  - Exchangeability does not hold across operating regimes, so calibrate per regime (cruise/climb/hot) or use
    weighted conformal, and report coverage per regime.
  - REMOVE-FROM-RUNTIME: sine-series calibration (engine_runtime.py:147-154), RUL formula (415), damage from the
    injected list (426-450).
Step 4.4 Mission reliability = P(RUL > remaining mission time), from the conformal distribution. Feeds status (M2)
  and the planner (M5).
Step 4.5 Maintenance:
  - wire backend/maintenance/work_package.py: hypotheses (posterior ≥ 0.7) and time-to-limit/RUL create a work order
    with ATA chapter, action from the registry, due time, parts;
  - sign-off flow (open -> in work -> signed off) persisted in var/maintenance.sqlite;
  - after sign-off, the fault clears and the health parameter reset is recorded.
Step 4.6 Adaptive learning (per tail):
  - the baseline mean/variance of each residual is updated with an EWMA only while status = GO for ≥ 30 min, no
    CUSUM above h/2 and no open work order;
  - twin nominal parameters are re-estimated the same way;
  - each update is versioned per tail with rollback;
  - the UI shows "baseline v7, updated 2 h ago".

R1. No .blend file is deleted, ever. Duplicates and old versions are MOVED to assets/blender/_archive/ with an entry in

R4. Git LFS with locking for .blend:
    - git lfs track --lockable "*.blend";
    - lock before editing (git lfs lock <file>), unlock after the push;
    - a push touching a file locked by someone else is rejected.
    This prevents two people overwriting each other's binary work (.blend files cannot be merged).
R5. Add "*.glb", "*.fbx" and "*.exr" to Git LFS for NEW commits. Do not rewrite history to move the old ones (that
    needs a force push, which we never do). The 5.1 GB .git stays as it is; it stops growing as fast.
R6. GLB files are BUILD OUTPUTS from the master .blend through the pipeline (5.4). Only one copy is committed
    (assets/web/engines/). Every app reads that one copy (via its build config or a copy step at build time). Before
    any duplicate GLB copy is removed from Git, the team confirms with md5 that it is byte-identical to the
    canonical copy.
R7. An asset register (assets/ASSET_REGISTER.csv) is the single truth for the team. Columns: engine_id, real engine
    name, master .blend path, md5, Blender version used, geometry status (REAL | REPRESENTATIVE | PLACEHOLDER),

PART 6 - USER EXPERIENCE THAT MAKES THE JUDGES (AND DRDO) REMEMBER IT
=====================================================================================================================

6.1 Principles from aviation and safety-critical standards (apply them; judges from DRDO/ADE will recognise them)
U1. Alert colours as on certified flight decks (14 CFR 25.1322, AC 25.1322-1, MIL-STD-411F is similar):
    - red = warning (NO-GO), amber/yellow = caution;
    - advisory = any colour other than red, amber, yellow or green (we use cyan);
    - red and amber are used for NOTHING else in the UI: no decorative red buttons, no amber accents.
    Action: audit the Tailwind theme and components; recolour every non-alert red/amber.
U2. Two-sense alerting for warnings and cautions: visual + aural.
    - One unique master-warning tone and one master-caution tone (as AC 25.1322-1 recommends).
    - The existing VoiceCopilot speaks the top reason ("Caution. Oil pressure low, engine two.").
    - Master warning/caution buttons acknowledge and silence.
U3. Alarm management (ISA-18.2 / EEMUA 191 benchmarks):
    - in nominal flight the target is about 1 new alert per 10 minutes on average; more than 10 per 10 minutes is a
      flood;
    - every alert must have an operator action, otherwise it is not an alert (it goes to the event log);
    - group child alerts under the root-cause hypothesis (one fault, one alert, details inside);
    - shelving with automatic un-shelve;
    - measure it: T-UX-3 counts alerts per 10 minutes in all four PS scenarios.
U4. Ecological Interface Design (EID): show the engine as purpose -> functions -> processes -> parts, the same
    hierarchy an engineer thinks in:
    - Purpose: can the aircraft complete the mission? (mission reliability, power margin, fuel/time margin)
    - Functions: produce power, reject heat, lubricate, supply fuel, supply electrical power. Each gets a margin bar.
    - Processes: the energy flows and pressures.
    - Parts: the 3D model.
    Clicking moves down the hierarchy. Research applying EID to digital twins and anomaly monitoring supports this.
U5. Predictions are actions. Every predictive alert says what will happen, when (with confidence), what to do, and
    which ATA reference applies. Example: "Oil cooler blockage likely (p=0.82). Oil temperature reaches 130 C in
    48 min (35-70). Reduce power to 75 % or land within 40 min. ATA 79."
U6. Honesty is visible:
    - every value has a provenance tooltip (TCDS / OM / DRDO / ASSUMED / CALIBRATED);
    - every screen shows its data source badge (SIM / REPLAY / CAN) and data age;
    - ASSUMED values are styled differently (dotted underline).
    DRDO evaluators value knowing which numbers are certified and which are estimates.

X2. GLASS ENGINE 3D:

X4. TIME MACHINE:
