1. THE GOAL IN ONE PAGE
=====================================================================================================================

When we are done, this is true (each line has a test in P Part 7):
  1. One physics simulation per engine (Rotax 912 iSc, 914, 915 iSc, Austro AE300, VRDE 2.2 L).
     - Power, temperatures, pressures, fuel flow, electrical values and vibration come from equations.
     - Each engine is calibrated to its certified data (power within 2 %).
     - Turbo engines hold power to their critical altitude.
     - No engine breaks its limits in normal cruise.
  2. Every fault (F01-F37, S01-S07) changes model parameters. Readings move because the physics runs. No fault
     "does nothing".
  3. The twin (UKF) tracks the engine. Detection, isolation (with cylinder) and explanation work from sensor
     evidence only. Sensor faults are recognised as sensor faults.
  4. Engine status (ENGINE OFF / GO / ADVISORY / CAUTION / NO-GO) follows limits, diagnosis and prognosis, with
     reasons. It never shows GO while something is wrong.
  5. RUL and time-to-limit come with calibrated 95 % bands (D18). There are mission reliability, maintenance work
     orders and adaptive baselines.
  6. A fault injected from anywhere shows the same everywhere within one tick, including the same 3D parts:
     console, 3D view, phone, Blender app, mission schedule, voice.
  7. Mission profiles (high altitude, endurance, hot weather, rapid throttle) and replay work. A sortie report is
     generated after each flight. The canyon route planner refuses infeasible routes and replans when engine health
     drops. Glide reachability and divert are available.
  8. CAN/FADEC, edge node, secure telemetry and federated learning run (simulated hardware, honest labels).
  9. The repository is clean: every folder has a purpose and its own AI guide, no .blend is lost, one copy of each
     model, one launcher.
 10. Nothing on screen is hard-coded. Adding a 6th engine or a new fault needs only config files (the
     "completely dynamic" rule, P Part 0).

2. GROUND RULES (short form - AGENTS.md has the full text)

Git:
  - Work only on Beta or beta/<card-id> branches made from Beta.
  - Never: commit, merge, rebase, reset or push main; reset --hard; push --force; git clean; checkout -- on files
    you did not change; stash other work.
  - Push only when Prasad asks.
  - Never delete a .blend (D1). "Remove" = stop using it, then git mv to archive_tracked/ after the replacement
    passes tests (D12).
  - Do not commit data/graph_db/fleet_graph.json until M0-11.
  - Commit at reasonable progress points (D22), judged by the situation: a coherent working unit.
    - Good points: the failing tests plus the code that makes them pass; a batch of moves with all references
      fixed; a finished document.
    - Not after every small edit, and never broken work.
    - Each commit keeps tests at or above the baseline and updates PROGRESS.txt RESUME HERE.
    - Message: "<card-id>: <what changed>".
  - NEVER any "Co-Authored-By: Claude" / AI attribution in commit messages or PRs, any branch (D24).
Truth (P Part 0):
  - No reading or limit typed into code.
  - No "or <number>" fallback.
  - Faults change parameters only.
  - Inference never reads truth.
  - No engine, fault or part names in code.
  - No invented engine data (ASSUMED + PROGRESS.txt).
  - No fake telemetry.
Tests:
  - Run the baseline first.
  - Write the failing test first.
  - Never weaken a test.
  - Every result is labelled SIMULATION / PUBLIC_PROXY / REAL_FLIGHT, with a baseline control and several seeds.
Current docs (D39): before using any library/tool/service API, check its CURRENT official docs via web search or
  web fetch, and record the URL + version in the PROGRESS entry. Never code an API from memory.
Order (D41): the production RAG/copilot (Phase 8b) comes after the main fixes. Phase 0 only archives the fabricated
  corpus.
Stop and ask Prasad (the AI must not decide alone):
  - new engine numbers;
  - anything that needs looking at a Blender model;
  - changing a pass criterion;
  - archiving a module another card uses;
  - code from origin/Prasad;
  - main, origin, LFS history or .blend files;
  - new dependencies.

3. HOW A SOLO DEVELOPER WORKS WITH AI
=====================================================================================================================

3.1 The session loop (one card per session)
  1. git switch Beta, then git switch -c beta/<card-id> (or reuse it if it exists).
  2. Start the AI session with the "Start a card" prompt (section 18.1).
  3. The AI reads AGENTS.md, DECISIONS.md, the last PROGRESS entry, the card, the named sections, and the AGENTS.md
     of the folders it will touch.
  4. The AI runs the baseline tests and shows the summary.
  5. The AI checks the current official docs of every library the card uses (D39), then proposes a plan: files,
     functions, tests, doc URLs. You approve or correct it. Use plan mode in Claude Code.
  6. The AI writes the tests first (shows them failing), implements in small steps, and runs the tests after each.
  7. The AI runs the "Done when" checks. You look at the running result yourself: open the UI, call the endpoint,
     watch the 3D view.
  8. The AI appends a PROGRESS.txt entry, updates RESUME HERE, and commits when the work is a coherent unit (D22).
     A card may end with one commit or several; a long card commits at each working milestone inside it.
  9. A fresh read-only AI session reviews the branch (section 3.4). Fix what it finds.
 10. Merge: git switch Beta, then git merge --no-ff beta/<card-id>. Run the phase's quick tests on Beta.

3.2 Size of a card
  Aim for something reviewable in one sitting: at most ~600 changed lines excluding generated files. The number of
  commits is decided by progress points (D22), not by a fixed count. If a card grows, split it (M1-07a, M1-07b) and
  note the split in PROGRESS.txt.

3.3 Parallel AI sessions (optional, solo-friendly)
  You can run two sessions at once only on different cards that touch different files.
  - Use git worktrees: git worktree add ../PS054-<card> beta/<card>.
  - Never run two sessions on the same worktree.
  - Never run two cards that both edit configs/faults.json, configs/engines/*.json or
    backend/server/state_schema.py at the same time.
  Good pairs:
  - backend physics + frontend view;
  - Blender scripts + docs;
  - evaluation harness + UI.

3.4 Second-opinion review (replaces the human reviewer)
  - Start a NEW session with no history.
  - Use the review prompt (section 18.3). It must report each checklist item of section 17 as yes/no with evidence.
  - Then run /code-review on the diff.
  - Fix the findings in the card session, not in the review session.

3.5 Keeping AI context healthy
  - Never paste whole R/A/P files. The cards name exact sections.
  - Long work: commit, end the session, start fresh with the PROGRESS entry as the hand-off.
  - If the AI loops or contradicts itself, use the "stuck" prompt (18.4), commit what works, and start fresh.
  - When a decision changes, add it to DECISIONS.md first, then continue.

3.6 Guard rails that run by themselves (card P0-02)
  - .claude/settings.json gets a PreToolUse hook. It blocks git push, reset --hard, git clean, any --force,
    switching to main, and deleting *.blend.
  - Read-only commands (git status/diff/log, pytest, tsc) are allowed without prompts.

17. REVIEW CHECKLIST AND AI RED FLAGS (used by the second-opinion session before every merge)
=====================================================================================================================

Checklist (all must be yes):
  [ ] Branch is beta/<card-id> from Beta; git log main -1 is still 9b5942e.
  [ ] The diff touches only the files the card names (+ tests). No unrelated reformatting.
  [ ] New tests fail before and pass after (output in the PROGRESS entry).
  [ ] No weakened test (git diff tests/: no raised tolerance, skip, deleted assert); ratchet baseline not raised.
  [ ] T-DYN-1 green: no new literal for a reading/limit, no "or <number>", no engine/fault/part name in code.
  [ ] New engine values are in configs with provenance; ASSUMED values listed in PROGRESS.txt.
  [ ] No deleted .blend: git diff --name-status Beta... | grep -E "^D.*\.blend$" is empty.
  [ ] Inference code does not import fault manager or sim truth (T-DYN-4 green; test_no_truth_leak list extended).
  [ ] Full pytest is no worse than the last PROGRESS baseline.
  [ ] The behaviour was seen running (endpoint called, UI looked at, or Blender opened), not only unit tests.
Red flags (reject and fix):
  - Numbers that match the test's expected values exactly, with no physics behind them.
  - try/except that swallows errors or returns a default "to keep the UI working".
  - Math.random / random.random in product code outside the seeded sim RNG.
  - A new implementation next to an existing module the card said to reuse.
  - "Calibrated" or "validated" in comments or docs without a test showing it.
  - Big refactors or renamed public functions the card did not ask for.
  - Edits to configs/faults.json or configs/engines/*.json by a card that does not own them.
  - Claims in docs copied from the idea text without a measured number behind them.
